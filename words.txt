ObjCSP
======

Go-style CSP for Objective-C: processes and channels, in the
lineage of Hoare (1978), occam (1980s) and Go.

The goal: push the complexity into the library. A client source
file should read as plainly as Go -- easily read process
definitions, easily read invocations, no block syntax.

Status, 2026-10-18: built. Everything below is implemented; what is
tested is listed under Verified, at the end.


Files:

	CSP.h      the library: everything a client file uses
	CSP.m      the implementation
	test.m     the tests (make check; make tsan for the race checker)
	fanout.m   a distributed worker written as a client (make fanout)
	bench/     the COOPER benchmark: Go, ObjCSP and linear ObjC
	           versions of the same job (cd bench; make) -- see
	           Performance

	A client file imports CSP.h -- after any other headers, because
	alt and otherwise are macros and would rewrite those words in
	anything imported later -- and compiles with CSP.m:

	    clang -fobjc-arc -o prog prog.m CSP.m -framework Foundation


Processes:

	A process is an ordinary C function. Nothing special in its
	definition; it usually takes the channel(s) it answers on.

	    void scoreWords(NSString *t, NSArray<NSString *> *v,
	                    Chan<WordScore *> *c) {
	        ...
	        [c send:r];
	    }

	go(...) starts one:

	    go(scoreWords(text, v, scores));

	The variables in the call are captured when go runs, so each
	process started in a loop gets that iteration's values. One
	difference from Go: a function call inside the arguments, like
	go(work([c receive])), runs in the new process, not before it
	starts. Do the call first, into a variable, and pass that.

	go({ ... }) runs a block of statements as a process -- Go's
	go func() { ... }():

	    go({
	        for (int i = 0; i < n; i++) [jobs send:@(i)];
	        [jobs close];
	    });

	Each process is its own thread, and the threads spread across
	all cores. A blocked process -- waiting on a channel -- uses no
	CPU and roughly 20-40 KB of memory (estimate, not measured).
	macOS allows 2,048 threads per program, so plan on at most
	about 2,000 live processes at once.

	When main returns, the program ends, and any processes still
	running end with it. Same as Go.


Channels:

	A channel is typed by what it carries -- any object type:

	    Chan<NSString *>   *lines   = chan();     // make(chan string)
	    Chan<WordScore *> *scores  = chan(nv);   // make(chan wordScore, nv)
	    Chan<Chan<Result *> *> *req = chan();     // channels of channels

	Objects only. An int is sent boxed, @(j), and read back with
	.intValue. Small numbers cost no allocation (tagged pointers).
	For a struct, write a small class -- see Structs.

	The type is checked by the compiler. A mismatch is a warning;
	build with -Werror to make it an error, as in Go. A bare Chan,
	no <...>, carries anything -- the equivalent of chan any.

	chan()  is unbuffered: send waits until a receiver has taken
	        the value. The two processes meet.
	chan(n) is buffered:   send waits only when n values are
	        already waiting to be received.


Send and receive:

	    [c send:r];                   // c <- r
	    WordScore *s = [c receive];  // s := <-c

	Both wait as long as they have to.

	A channel passes a reference, not a copy. After sending an
	object, stop changing it -- or send immutable objects
	(NSString, NSArray) rather than mutable ones.

	nil can't be sent. [c send:nil] is an error. That's what lets
	nil from receive mean one thing only: closed.


Structs:

	Be a good citizen: where Go would use a struct, write a small
	class, and send objects.

	    @interface Sample : NSObject
	    @property int day;
	    @property double weight;
	    @end
	    @implementation Sample
	    @end

	    Chan<Sample *> *c = chan();

	The channel carries your own type name, the compiler checks
	every send and receive, and fields can be anything -- strings,
	arrays, other objects -- kept alive properly.

	The escape hatch, for a C struct you already have (from C
	code, or an Apple API), is a Parcel. It holds a copy of the
	struct's bytes and remembers which struct type they came from.

	    typedef struct { int day; double weight; } Sample;

	    Chan<Parcel *> *c = chan();

	    [c send:parcelFromStruct(s)];
	    Sample got = structFromParcel(Sample, [c receive]);

	structFromParcel checks the type: asking for a Sample from a
	Parcel that holds something else is an error, not garbage.

	The receiver gets its own copy. Unlike an object, a struct
	sent in a Parcel is not shared, so the sender may go on
	changing s.

	Plain data only -- ints, doubles, fixed arrays of them. A
	pointer inside the struct (an NSString *, a char *) is copied
	as a bare address; what it points to is neither copied nor
	kept alive. For a struct like that, use a small class instead.

	Both are macros, not methods: a method can't take or return
	"any struct", a macro can.

	A Parcel channel is Chan<Parcel *> whatever struct it carries,
	so the compiler can't tell a Sample channel from any other;
	the check happens when the struct comes out. A per-struct
	parcel class, checked by the compiler, is a possible later
	addition.


Close and range:

	    [c close];

	Means "no more values." Receivers still get anything already
	in the channel, then nil from then on. Sending on a closed
	channel is an error; so is closing one twice.

	    for (NSNumber *j in jobs) {   // for j := range jobs
	        train(j.intValue);
	    }

	Receives until the channel is closed and empty, then the loop
	ends. Several processes can range over the same channel; each
	value goes to exactly one of them. That's a work queue.

	To say "nothing" on a signal channel, where the message itself
	carries no data, send [NSNull null] on a Chan<NSNull *> -- the
	equivalent of Go's chan struct{}. Rarely needed.


alt -- Go's select:

	alt waits on several channel operations at once and runs
	whichever is ready first. If several are ready together, it
	picks one at random.

	    alt {
	        receive(r, results) { use(r); }
	        receive(q, quit)    { stop = YES; }
	        after(2.0)          { NSLog(@"story timed out"); }
	    }

	The cases:

	receive(x, c) { }   a value arrived on c. x is declared for
	                    you, typed from the channel, scoped to the
	                    body. On a closed channel this fires with
	                    x nil.

	sending(c, v) { }   v was delivered on c. The body is often
	                    empty -- delivering was the point.

	after(secs) { }     nothing else was ready within secs seconds.

	otherwise { }       nothing is ready right now. With this case
	                    alt never waits.

	A body is ordinary code. return returns from the enclosing
	function. break ends the case only, not a surrounding loop --
	the same trap as Go; use a flag to leave a loop.

	Every case must be written directly inside the alt -- not
	inside an if. (alt runs its body twice, first to learn the
	cases, then to run the chosen one; a case that appears on only
	one pass confuses it.) A case's channel and value are evaluated
	once.

	A case on a nil channel is never ready, as in Go: setting a
	channel variable to nil switches its case off.

	alt {} with no cases waits forever, as Go's select {} does.

	Named alt, occam's word, because select is already a POSIX
	function.


The four alt patterns:

	1. Anything waiting? (e.g. a ctrl-c check between rounds)

	    alt {
	        receive(s, sigc) { save(); return; }
	        otherwise        { }
	    }

	2. Work or stop.

	    for (;;) {
	        alt {
	            receive(j, jobs) { train(j.intValue); }
	            receive(d, done) { return; }
	        }
	    }

	3. Timeout.

	    alt {
	        receive(line, c) { use(line); }
	        after(2.0)       { NSLog(@"story timed out"); }
	    }

	4. Deliver or stop. Without alt, [out send:s] would wait
	   forever if nobody takes s, and never hear quit.

	    for (Story *s in stories) {
	        alt {
	            sending(out, s)  { }
	            receive(q, quit) { return; }
	        }
	    }


A distributed worker -- fan out, collect the answers:

	Hand each piece of work to its own process; every process
	answers on one shared channel; collect exactly as many answers
	as processes were started.

	Go:

	    nv := len(lists)
	    scores := make(chan wordScore, nv)
	    for _, v := range lists {
	        go scoreWords(text, v, scores)
	    }
	    for i := 0; i < nv; i++ {
	        score := <-scores
	        ...
	    }

	ObjCSP:

	    NSUInteger nv = lists.count;
	    Chan<WordScore *> *scores = chan(nv);
	    for (NSArray<NSString *> *v in lists)
	        go(scoreWords(text, v, scores));
	    for (NSUInteger i = 0; i < nv; i++) {
	        WordScore *score = [scores receive];
	        ...
	    }


Left out, on purpose:

	Send-only / receive-only channel views (Go's chan<- and
	<-chan). One plain Chan does everything.

	Go's v, ok := <-c. Not needed: nil can't be sent, so nil means
	closed.

	A scheduler multiplexing processes over a few threads, the way
	Go does. Left out at first as only worth it past ~2,000 live
	processes -- but see Performance: it is also what small
	processes need. Now an open question.

	Channels of plain C values (Chan of int). Box ints as @(j);
	make structs into small classes, or carry existing C structs
	in a Parcel.


Decisions, 2026-10-18:

	one thread per process -- memory isn't the constraint; the
	    2,048-thread cap is
	short names: Chan, chan, go, alt -- readability over Cocoa's
	    prefix convention
	typed channels, any object type
	nil can't be sent; nil from receive means closed
	full select, as alt, written with macros rather than blocks --
	    blocks needed ^(Type *x){ }, __block flags, and couldn't
	    return from the function
	timeouts (after) in the first version
	structs: write a small class and send objects -- the main
	    path. Parcel kept as the escape hatch for existing C
	    structs: parcelFromStruct(s),
	    structFromParcel(Type, p). "Unpack" was rejected -- it
	    suggests ending up with a richer object, not the same
	    flat struct. Parcel over Packet: delivery, not networking.
	    Our own class, not an NSValue subclass (NSValue is a
	    class cluster); it adds a runtime type check.


Performance, 2026-10-18 -- the COOPER benchmark:

	The job: a 1,000-character lowercase lorem ipsum block. 1,000
	processes each take it from a channel, overwrite 5 random
	spots with "COOPER", and send it back on a second channel;
	main collects all 1,000 and writes them to /dev/null. The
	same job three ways, in bench/:

	    cooper.go    Go, goroutines
	    cooper.m     ObjCSP, line for line with the Go
	    linear.m     ObjC, 1,000 plain calls on main

	All three checked first: 1,000 distinct blocks of exactly
	1,000 characters. (Some show 3 or 4 COOPERs, not 5: a random
	spot can land on an earlier one.)

	One trial, median ms (5 runs x 21 trials, this Mac: 8 cores,
	Intel, macOS 12; Go 1.19):

	                     cold    warm    whole program, 21 trials
	    Go               2.9     2.2      51 ms
	    ObjCSP          23.6    21.6     592 ms
	    ObjC linear      5.5     4.4     107 ms

	ObjCSP is about 10x slower than Go and 5x slower than doing
	the work in a straight line. Where its 21 ms goes, warm:

	    spawn     ~9.5 ms   creating 1,000 kernel threads, ~9.5 us each
	    send      ~2.7 ms   each handoff wakes a sleeping thread
	    collect   ~9.5 ms   each take wakes the sender's thread so it
	                        can finish and exit

	Each block is about 4 us of work. ObjCSP spends about 20 us of
	kernel time per process around it: creating a thread, and
	waking one for every message. Go does both in user space.
	Spare cores can't win that back when the work is this small.

	Threads are fine when each process does real work -- scoring
	a story takes far longer than starting a thread. They are
	expensive for many tiny processes, which is exactly the "let
	'em rip" style: start one per piece of work, never a pool.

	The two fixes, still to decide:

	thread reuse     a finished process's thread parks, and the
	                 next go() takes it. Small and safe. But it
	                 can't help here: all 1,000 processes are alive
	                 at once, so 1,000 threads must exist. It helps
	                 programs that start processes over time.

	a scheduler      processes become coroutines with small stacks,
	                 run by ~8 threads, one per core; a blocked
	                 process switches to another in user space.
	                 How Go does it, and the real fix -- client
	                 code unchanged. The cost: hand-written context
	                 switching, and a process blocking outside our
	                 channels (a file read, sleep, a lock) stalls
	                 one of the 8 threads. Timers move into the
	                 scheduler.


Known limits:

	A for (x in c) loop left early with break keeps its last value
	alive -- one object, never freed. Harmless unless done in a
	loop of its own, many times over.

	The compiler checks receive and send:, but not the value in a
	sending(c, v) case; a wrong type there is caught nowhere.

	Two anonymous structs with the same fields look like the same
	type to a Parcel. Give a struct a tag name (typedef struct
	Sample { ... } Sample) and the check can tell them apart.


Verified, 2026-10-18 (test.m, 47 checks; 100 runs clean, and clean
under ThreadSanitizer):

	unbuffered send waits for the receiver
	buffered channels: FIFO order, capacity
	close: drain, then nil; a waiting receiver gets nil; errors on
	    send-after-close, double close, and sending nil -- which
	    the compiler also warns about
	for-in as a work queue: 4 workers, 1,000 values, each once
	alt: random choice among ready cases (about 50/50 over 1,000);
	    otherwise only when nothing is ready; a nil channel's case
	    never fires; after's timing
	    (0.200-0.205 s for 0.2); sending; deliver-or-stop; receive
	    on a closed channel fires with nil; return from a case
	receive(x, c) types x from Chan<T> -- checked at compile time
	a case that never fires leaves nothing queued, over 5,000 alts
	Parcel: round trip, the copy, wrong-type and closed-channel
	    errors; anonymous structs alike, tagged ones told apart
	1,900 processes live at once: started in about 0.02 s
	stress: 6 senders, 5 receivers, 3 unbuffered channels, all
	    through alt -- 18,000 values, each received exactly once;
	    6 processes offering both sending and receive on one
	    channel -- sends and receives balance

	The first stress runs failed about one in three: each process
	reported two numbers as two sends on a shared channel, and
	reports from different processes interleaved. A test bug, not
	a library one -- the fix was one message per report. Worth
	remembering as a pattern: a reply that must stay together goes
	in one message.
