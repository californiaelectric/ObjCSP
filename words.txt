ObjCSP
======

Go-style CSP for Objective-C: processes and channels, in the
lineage of Hoare (1978), occam (1980s) and Go.

The goal: push the complexity into the library. A client source
file should read as plainly as Go -- easily read process
definitions, easily read invocations, no block syntax.

Status, 2026-10-18: built, with the scheduler -- processes are
coroutines run by one worker thread per core. The first version,
one thread per process, remains as CSP_DEBUG=threads. Intel Macs
only for the scheduler so far; other CPUs run a thread per
process. Installed as a library. What is tested is listed under
Verified, at the end.


Files:

	CSP.h          the library: everything a client file uses
	CSP.m          channels, ALT, Parcel
	CSPSched.h     internal: how a waiting process sleeps and wakes
	CSPSched.m     the scheduler, and the thread-per-process fallback
	csp_x86_64.S   the context switch, for Intel
	test.m         the tests: make check builds and runs csptest;
	               make tsan, the same under the race checker
	fanout.m       a distributed worker written as a client
	               (make fanout)
	bench/         three benchmarks, each in Go and ObjCSP, with
	               and without concurrency (cd bench; make data;
	               make) -- see Performance
	examples/      verify.m: re-verify a SQLite database of people,
	               one process per person and one writer process
	               (cd examples; make; ./verify create; ./verify csp)

	The deliverable is a static library, libcsp.a, and its header,
	CSP.h. The library is universal -- one file for Intel and Apple
	Silicon Macs; on Apple Silicon it runs a thread per process
	until the scheduler is ported there. Build and install once:

	    make
	    sudo make install       # libcsp.a to /usr/local/lib,
	                            # CSP.h to /usr/local/include

	(sudo because /usr/local is owned by root here. Not /usr/lib:
	System Integrity Protection makes it read-only, even to sudo.
	make uninstall removes both files.)

	clang and the linker search /usr/local/include and
	/usr/local/lib on their own, so a client needs no path flags.
	It imports CSP.h -- after any other headers, because ALT and
	OTHERWISE are macros and would rewrite those words in anything
	imported later -- and links the library:

	    #import "CSP.h"

	    clang -fobjc-arc -o prog prog.m -lcsp -framework Foundation

	The library's code is copied into prog when it's built, so prog
	runs anywhere with nothing installed. After a new make install,
	rebuild a program to pick up the new library. ARC is required
	(-fobjc-arc; Xcode's default).


Processes:

	A process is an ordinary C function. Nothing special in its
	definition; it usually takes the channel(s) it answers on.

	    void scoreWords(NSString *t, NSArray<NSString *> *v,
	                    Chan<WordScore *> *c) {
	        ...
	        [c send:r];
	    }

	go(...) starts one:

	    go(scoreWords(text, v, scores));

	The variables in the call are captured when go runs, so each
	process started in a loop gets that iteration's values. One
	difference from Go: a function call inside the arguments, like
	go(work([c receive])), runs in the new process, not before it
	starts. Do the call first, into a variable, and pass that.

	A message to an object works the same way -- any object, any
	method, from anywhere, self included:

	    go([downloader fetch:url into:results]);
	    go([self scoreDocument:doc]);

	The receiver and arguments are kept alive until the process
	finishes. The return value is dropped, as in Go -- pass a
	channel to get a result back. The object is shared, not
	copied: if the caller and the process both change it at once,
	that's a race, as in Go.

	go({ ... }) runs a block of statements as a process -- Go's
	go func() { ... }():

	    go({
	        for (int i = 0; i < n; i++) [jobs send:@(i)];
	        [jobs close];
	    });

	go() can't capture a C array: go(f(fds[0])) with int fds[2]
	won't compile. Copy what's needed into plain variables first --
	int readEnd = fds[0] -- and pass those. (Go copies arrays; a
	block can't.)

	Processes run on the scheduler: coroutines, run by one worker
	thread per core, so they spread across all cores. A process
	waiting on a channel uses no CPU and no thread -- just its
	stack, of which only the pages it touched use memory. 20,000
	live at once start in about 0.12 s. (With CSP_DEBUG=threads each
	process is a thread again, and macOS's 2,048-thread limit
	applies.)

	    sleepFor(seconds)    pause this process; the others go on
	    yield()              let others run, for a long computation

	Use sleepFor, not sleep() or [NSThread sleepForTimeInterval:]:
	those hold up a whole worker -- see The hazards, 2.

	When main returns, the program ends, and any processes still
	running end with it. Same as Go.


Channels:

	A channel is typed by what it carries -- any object type:

	    Chan<NSString *>   *lines   = chan();     // make(chan string)
	    Chan<WordScore *> *scores  = chan(nv);   // make(chan wordScore, nv)
	    Chan<Chan<Result *> *> *req = chan();     // channels of channels

	Objects only. An int is sent boxed, @(j), and read back with
	.intValue. Small numbers cost no allocation (tagged pointers).
	For a struct, write a small class -- see Structs.

	The type is checked by the compiler. A mismatch is a warning;
	build with -Werror to make it an error, as in Go. A bare Chan,
	no <...>, carries anything -- the equivalent of chan any.

	chan()  is unbuffered: send waits until a receiver has taken
	        the value. The two processes meet.
	chan(n) is buffered:   send waits only when n values are
	        already waiting to be received.


Send and receive:

	    [c send:r];                   // c <- r
	    WordScore *s = [c receive];  // s := <-c

	Both wait as long as they have to.

	A channel passes a reference, not a copy. After sending an
	object, stop changing it -- or send immutable objects
	(NSString, NSArray) rather than mutable ones.

	nil can't be sent. [c send:nil] is an error. That's what lets
	nil from receive mean one thing only: closed.


Structs:

	Be a good citizen: where Go would use a struct, write a small
	class, and send objects.

	    @interface Sample : NSObject
	    @property int day;
	    @property double weight;
	    @end
	    @implementation Sample
	    @end

	    Chan<Sample *> *c = chan();

	The channel carries your own type name, the compiler checks
	every send and receive, and fields can be anything -- strings,
	arrays, other objects -- kept alive properly.

	The escape hatch, for a C struct you already have (from C
	code, or an Apple API), is a Parcel. It holds a copy of the
	struct's bytes and remembers which struct type they came from.

	    typedef struct { int day; double weight; } Sample;

	    Chan<Parcel *> *c = chan();

	    [c send:parcelFromStruct(s)];
	    Sample got = structFromParcel(Sample, [c receive]);

	structFromParcel checks the type: asking for a Sample from a
	Parcel that holds something else is an error, not garbage.

	The receiver gets its own copy. Unlike an object, a struct
	sent in a Parcel is not shared, so the sender may go on
	changing s.

	Plain data only -- ints, doubles, fixed arrays of them. A
	pointer inside the struct (an NSString *, a char *) is copied
	as a bare address; what it points to is neither copied nor
	kept alive. For a struct like that, use a small class instead.

	Both are macros, not methods: a method can't take or return
	"any struct", a macro can.

	A Parcel channel is Chan<Parcel *> whatever struct it carries,
	so the compiler can't tell a Sample channel from any other;
	the check happens when the struct comes out. A per-struct
	parcel class, checked by the compiler, is a possible later
	addition.


Close and range:

	    [c close];

	Means "no more values." Receivers still get anything already
	in the channel, then nil from then on. Sending on a closed
	channel is an error; so is closing one twice.

	    for (NSNumber *j in jobs) {   // for j := range jobs
	        train(j.intValue);
	    }

	Receives until the channel is closed and empty, then the loop
	ends. Several processes can range over the same channel; each
	value goes to exactly one of them. That's a work queue.

	Each pass of the loop runs in its own autorelease pool, drained
	before the next value is received. A worker can loop over a
	million jobs without growing, and without an @autoreleasepool
	of its own. Cost: 2-18 ns a pass, measured with an almost empty
	body -- nothing next to a channel operation.

	To say "nothing" on a signal channel, where the message itself
	carries no data, send [NSNull null] on a Chan<NSNull *> -- the
	equivalent of Go's chan struct{}. Rarely needed.


ALT -- Go's select:

	ALT waits on several channel operations at once and runs
	whichever is ready first. If several are ready together, it
	picks one at random.

	    ALT {
	        receive(r, results) { use(r); }
	        receive(q, quit)    { stop = YES; }
	        after(2.0)          { NSLog(@"story timed out"); }
	    }

	The cases:

	receive(x, c) { }   a value arrived on c. x is declared for
	                    you, typed from the channel, scoped to the
	                    body. On a closed channel this fires with
	                    x nil.

	sending(c, v) { }   v was delivered on c. The body is often
	                    empty -- delivering was the point.

	after(secs) { }     nothing else was ready within secs seconds.

	OTHERWISE { }       nothing is ready right now. With this case
	                    ALT never waits.

	A body is ordinary code. return returns from the enclosing
	function. break ends the case only, not a surrounding loop --
	the same trap as Go; use a flag to leave a loop.

	Every case must be written directly inside the ALT -- not
	inside an if. (ALT runs its body twice, first to learn the
	cases, then to run the chosen one; a case that appears on only
	one pass confuses it.) A case's channel and value are evaluated
	once.

	A case on a nil channel is never ready, as in Go: setting a
	channel variable to nil switches its case off.

	ALT {} with no cases waits forever, as Go's select {} does.

	Named ALT, occam's word, because select is already a POSIX
	function -- and in capitals, as occam wrote it and as C writes
	macros. ALT and OTHERWISE are the two macros that rewrite their
	word wherever it appears; capitals make a clash with ordinary
	code much less likely (lowercase alt is a struct field in
	Apple's <printf.h>). The case words -- receive, sending, after
	-- only expand when followed by (, so they stay lowercase.


The four ALT patterns:

	1. Anything waiting? (e.g. a ctrl-c check between rounds)

	    ALT {
	        receive(s, sigc) { save(); return; }
	        OTHERWISE        { }
	    }

	2. Work or stop.

	    for (;;) {
	        ALT {
	            receive(j, jobs) { train(j.intValue); }
	            receive(d, done) { return; }
	        }
	    }

	3. Timeout.

	    ALT {
	        receive(line, c) { use(line); }
	        after(2.0)       { NSLog(@"story timed out"); }
	    }

	4. Deliver or stop. Without ALT, [out send:s] would wait
	   forever if nobody takes s, and never hear quit.

	    for (Story *s in stories) {
	        ALT {
	            sending(out, s)  { }
	            receive(q, quit) { return; }
	        }
	    }


A distributed worker -- fan out, collect the answers:

	Hand each piece of work to its own process; every process
	answers on one shared channel; collect exactly as many answers
	as processes were started.

	Go:

	    nv := len(lists)
	    scores := make(chan wordScore, nv)
	    for _, v := range lists {
	        go scoreWords(text, v, scores)
	    }
	    for i := 0; i < nv; i++ {
	        score := <-scores
	        ...
	    }

	ObjCSP:

	    NSUInteger nv = lists.count;
	    Chan<WordScore *> *scores = chan(nv);
	    for (NSArray<NSString *> *v in lists)
	        go(scoreWords(text, v, scores));
	    for (NSUInteger i = 0; i < nv; i++) {
	        WordScore *score = [scores receive];
	        ...
	    }


Left out, on purpose:

	Send-only / receive-only channel views (Go's chan<- and
	<-chan). One plain Chan does everything.

	Go's v, ok := <-c. Not needed: nil can't be sent, so nil means
	closed.

	(A scheduler was left out at first, as only worth it past
	~2,000 live processes. The COOPER benchmark showed it is also
	what small processes need, and it is now built -- see The
	scheduler.)

	Channels of plain C values (Chan of int). Box ints as @(j);
	make structs into small classes, or carry existing C structs
	in a Parcel.


Decisions, 2026-10-18:

	one thread per process -- memory isn't the constraint; the
	    2,048-thread cap is. Later overturned by the COOPER
	    benchmark: the cost that matters is kernel time per
	    process and per message. See The scheduler.
	short names: Chan, chan, go, ALT -- readability over Cocoa's
	    prefix convention
	typed channels, any object type
	nil can't be sent; nil from receive means closed
	full select, as ALT, written with macros rather than blocks --
	    blocks needed ^(Type *x){ }, __block flags, and couldn't
	    return from the function
	timeouts (after) in the first version
	structs: write a small class and send objects -- the main
	    path. Parcel kept as the escape hatch for existing C
	    structs: parcelFromStruct(s),
	    structFromParcel(Type, p). "Unpack" was rejected -- it
	    suggests ending up with a richer object, not the same
	    flat struct. Parcel over Packet: delivery, not networking.
	    Our own class, not an NSValue subclass (NSValue is a
	    class cluster); it adds a runtime type check.
	the deliverable: a static library, libcsp.a + CSP.h, installed
	    in /usr/local -- see Files
	the scheduler: coroutines on one worker per core, all cores
	    from the start, brought up at CSP_MAXPROCS=1 -- see The
	    scheduler and The hazards
	ALT and OTHERWISE in capitals, the rest lowercase -- see ALT.
	    go stays go: it reads as Go does, libmill and libdill use
	    it, and it only expands before (. Not par: occam's PAR
	    waits for all its parts to finish, go doesn't wait. (A
	    real PAR block that waits for all is a possible later
	    addition.) Not spawn: an ugly word.
	settings named after Go: CSP_MAXPROCS (GOMAXPROCS) and
	    CSP_DEBUG=threads (GODEBUG) -- not CSP_THREADS=1, which
	    read as switching a feature on rather than the good thing
	    off


Performance, 2026-10-18:

	Three benchmarks in bench/, each written four ways -- Go with
	goroutines, Go in a straight line, ObjCSP, and ObjC in a straight
	line -- plus ObjCSP with CSP_DEBUG=threads. Every version's
	output is checked against Go's, byte for byte, before timing.
	This Mac: 8 cores (likely 4 physical), Intel, macOS 12; Go 1.19.

	COOPER -- tiny work. A 1,000-character lowercase lorem ipsum
	block; 1,000 processes each take it from a channel, write
	"COOPER" over 5 spots, and send it back; main collects them all
	and writes them to /dev/null. Process i's spots are
	(i*7919 + k*104729) mod 995, k = 0..4. (They were random at
	first, but macOS's arc4random is behind one lock for the whole
	program, and 8 workers queued on it -- the benchmark was
	measuring the random-number generator.) Warm, median of
	5 runs x 21 trials:

	    Go, goroutines       1.9 ms
	    Go, linear           0.6 ms
	    ObjCSP               5.5 ms
	    ObjCSP, threads     23.7 ms
	    ObjC, linear         3.6 ms

	Everyone loses to a straight line here, Go by more (3x) than
	ObjCSP (1.5x): the work per block is smaller than a handoff.
	What COOPER measures is the cost per process -- start it, give
	it the block, take the result: about 2 us for ObjCSP, 1.25 us
	for Go. With a thread per process it was about 20 us.

	Models -- real computation. 1,000 independent linear
	classifiers over one generated dataset, 400 samples x 256
	features; one process per model trains it for 10 passes, about
	a million multiply-adds, a few ms. Median of 5 runs x 3 trials:

	    Go, goroutines       193 ms
	    Go, linear          1172 ms
	    ObjCSP               180 ms
	    ObjCSP, threads      206 ms
	    ObjC, linear        1066 ms

	ObjCSP 5.9x over its straight line, Go 6.1x -- about all this
	Mac has -- and ObjCSP slightly faster than Go: the same
	arithmetic, and the cost per process vanishes next to
	milliseconds of work.

	Documents -- nested fan-out with files and strings. 2,000
	generated documents of made-up words, 2-20 KB each (make data),
	and 9 categories of 40 words. One process per document reads
	its file and splits it into words, then starts one process per
	category to count the document's words in it; the document goes
	to the category with the most. Up to 20,000 processes at once.
	Median of 5 runs x 3 trials:

	    Go, goroutines       374 ms
	    Go, linear          1377 ms
	    ObjCSP              1032 ms
	    ObjCSP, threads     can't run -- past the 2,048-thread limit
	    ObjC, linear        2593 ms

	ObjCSP 2.5x over its straight line, Go 3.7x in that run. About
	1.9x of the gap to Go is Foundation itself -- the straight lines
	show it: NSString splitting and NSSet lookups against Go's
	strings and maps.

	The rest -- weaker scaling -- was looked into, 2026-10-18:

	    measured again, Go and ObjCSP alternating round by round so
	        both see the same conditions: Go 2.98x, ObjCSP 2.47x.
	        Go's 3.7x was a good moment on this machine, which
	        slows its clock when every core is busy (about 10 W).
	        The real gap in scaling is about 20%.
	    the nano allocator (MallocNanoZone): no effect -- 2.39-2.45x
	        unset, on or off. (This session's shell had
	        MallocNanoZone=0 set; every earlier run inherited it.)
	    reference counting on shared objects: barely in the sample.
	    stacks: with up to 20,000 processes alive, all but 1,024
	        finished stacks were unmapped and later mapped again.
	        Unmapping interrupts every other core running the
	        program, and showed in the sample (munmap, mmap,
	        mprotect). Stacks now stay mapped -- see Known limits --
	        but offering their pages back costs about the same; only
	        keeping every one exactly as it is gained anything (~6%),
	        at the price of holding ~150 MB for good. Not taken.
	    what's left is Foundation's own work: containsObject:,
	        string hashing, objc_msgSend, splitting -- the job
	        itself, scaling a little less well than Go's simpler
	        strings and maps on this machine. Not something the
	        scheduler can fix. A Mac with more cores and power
	        would say more.

	Waiting against computing -- CSP_MAXPROCS. examples/verify.m
	re-verifies 1,000 people in a SQLite database: each check is a
	format test plus a 1-20 ms wait standing in for a mail server,
	and one writer process stamps the verified ones in batches.

	    verify, csp        0.03 s   (921 stamped, 79 bad addresses)
	    verify, linear    12.4  s   (the same 921 and 79)
	    verify, sql        0.003 s  (one UPDATE, no checks -- the
	                                 right tool when there's no work
	                                 per record)

	                     verify (waiting)    models (computing)
	    CSP_MAXPROCS=1       0.030 s            1102 ms
	    CSP_MAXPROCS=2       0.028 s             550 ms   2.0x
	    CSP_MAXPROCS=4       0.028 s             278 ms   4.0x
	    CSP_MAXPROCS=8       0.030 s             167 ms   6.6x

	Waiting gains nothing from cores: a process in sleepFor holds
	no worker, so one worker keeps all 1,000 waits going. Computing
	gains from every core, until the hardware runs out. This Mac's
	i5-1030NG7 has 4 cores with 2 hardware threads each; macOS fills
	the 4 cores first, and the second threads helped models a lot
	(1.66x from 4 to 8) only because its dot product is one chain of
	dependent additions that leaves gaps for a sibling thread. It
	also runs on about 10 W, so with every core busy it slows its
	clock.

	Where processes start to pay -- the crossover. examples/
	objects.m makes 10,000 objects; each sets a value and calls a
	method that computes from it, a chain of xorshift steps that
	can't be skipped. Every version's checksum is the same.

	    work per object        processes   loop      processes vs loop
	    none                   0.032 s     0.002 s   loop 20-80x faster
	    1,000 steps,  ~3 us    0.028 s     0.030 s   about even
	    10,000 steps, ~28 us   0.063 s     0.289 s   processes 4.6x
	    100,000 steps, ~280 us 0.452 s     2.882 s   processes 6.4x

	(Times are for main making the objects and each process setting
	and computing one; processes making their own objects came out
	the same above 1,000 steps.) On this Mac: give a piece of work
	its own process once it takes more than a few microseconds --
	parsing a file, an image, a query, a network call. Setting a
	property or adding two numbers belongs in a loop. Go's
	crossover is similar, a little lower.

	How COOPER got from 21.6 ms (threads) to 5.5 ms (scheduler), each
	step found by sampling the running program (macOS's sample):

	    the scheduler itself                     24.6 -> 13.7 ms
	    a worker that runs out of work looks
	        again for 50 us before sleeping, and
	        only wakes a sleeping one if none is
	        looking; main does the same before
	        sleeping on its semaphore             13.7 -> ~11 ms
	    the library's locks try for a moment
	        before sleeping: they are held for
	        well under a microsecond, but a busy
	        pthread mutex sleeps in the kernel
	        at once                               ~11 -> 6.3 ms
	    the benchmark's random spots made fixed   6.3 -> 5.5 ms


The scheduler, 2026-10-18 -- built:

	Goal: let 'em rip at Go's cost. One process per piece of work,
	thousands at once, using every core -- with client code exactly
	as it is now.

	The idea. A process becomes a coroutine: its own stack and a
	saved set of CPU registers. A few worker threads, one per core,
	run them. When a process waits on a channel, its worker saves
	its registers and loads another runnable process's -- a switch
	in user space, no kernel involved. How Go does it.

	All cores from the start. A separate single-thread version
	(libmill's choice, which dodges the hard parts) was considered
	and dropped: a CSP runtime that doesn't use every core isn't
	worth having. One worker is still the first setting the real
	scheduler runs at -- see Building it.

	The parts:

	context switch   save one process's registers and stack
	                 pointer, load another's. Hand-written per CPU
	                 type -- ~20 lines on Intel; Apple Silicon gets
	                 its own. Not ucontext: deprecated, and a kernel
	                 call per switch.

	stacks           1 MB per process, reserved address space --
	                 real memory only for pages touched, a few KB
	                 for most. A guard page below each, so an
	                 overflow stops at once, with a clear message:
	                 "process stack overflow (1 MB)". No growth as
	                 in Go: C keeps raw pointers into its stack. The
	                 2,048-process cap goes away.

	workers          one per core, counted at startup
	                 (activeProcessorCount). CSP_MAXPROCS=n
	                 overrides, as GOMAXPROCS does.

	channels         unchanged in logic. Today a blocked process
	                 sleeps on a semaphore and whoever completes it
	                 signals; under the scheduler "sleep" becomes
	                 "switch to another process" and "signal"
	                 becomes "put it back on the run queue". Waiters,
	                 claims, ALT and close stay as they are.

	timers           after and sleepFor deadlines in one sorted
	                 list; an idle worker sleeps until the earliest.

	main             not a coroutine. When main (or any plain
	                 thread) blocks on a channel it uses today's
	                 semaphore path. Both paths coexist.

	The experiment -- does Objective-C allow it at all? The go/no-go
	question was autorelease pools. The runtime keeps a pool stack
	per thread; coroutines interleave on threads and move between
	them. Tested outside the library (a throwaway experiment, not
	kept in the repo), macOS 12, Intel:

	    the pool stack is one pointer in one thread-local slot
	        (slot 43 here)
	    without swapping it per coroutine, two coroutines
	        interleaving pools on one thread abort the runtime:
	        "autorelease pool page corrupted"
	    swapping it on every switch: 0 failures over 100 rounds --
	        half with every step on a brand-new thread (a pool
	        opened on one thread, filled on another, closed on a
	        third; 3,000 objects per pool, several pages) -- and
	        clean under the runtime's own pool debugging modes
	    a switch costs 11.6 ns; the pool swap adds ~0.1 ns.
	        Today's thread wake costs several microseconds.

	The slot number is private to the runtime, so it is found at
	startup, never hard-coded: on a throwaway thread, open a pool
	and autorelease an object; the pool slot is the one whose value
	is the start of the page holding a fresh push token. Exactly
	one match, then a swap test on it -- open a pool on a swapped-in
	empty stack, swap back, check the original pool still frees its
	object. Any failure: fall back to a thread per process, with a
	one-line warning.

	What the experiment missed. Each pool page also records the
	thread that made it, and the runtime checks that when it frees
	the page -- "autorelease pool page corrupted ... pthread X
	should be Y" -- so a process that made a page on one worker and
	freed it on another aborted the program. The experiment passed
	by coincidence: each of its threads exited before the next
	started, and macOS reused the same thread record. Found when
	building the scheduler, reproduced every run by a test that
	frees pages on a different worker. The fix: the startup probe
	also finds where a page keeps its thread and its links to the
	pages before and after it (fill a page until a second starts;
	each field must match exactly once), and when a process
	continues on a different thread than last time, its pages --
	usually one or two -- are handed to that thread. Staying on the
	same worker costs nothing.


The hazards, and what was decided:

	1. A lock held across a channel operation. A process can pause
	   holding it and continue on another worker: unlocking from
	   the wrong thread, deadlock, or -- with @synchronized and
	   recursive locks -- two processes inside at once.
	   Decided: a rule. Don't hold a lock across a channel
	   operation; share by communicating. No library lock --
	   channels collect results, and that's all this style needs.
	   Foundation's own locks are safe: taken and released inside
	   one call.

	2. Blocking outside the channels -- sleep, a file read, a
	   network call. It stops the whole worker, not just the
	   process; if all workers wait on something another process
	   must do, everything stops.
	   Decided: a monitor thread, as Go has. When a worker has run
	   one process for ~10 ms and the kernel says that thread is
	   waiting, the monitor starts an extra worker. Blocking calls
	   just work -- read the file right there in the process. Plus
	   sleepFor(seconds), which pauses only the process.

	3. "The current thread" changes mid-function. A process can
	   start on one worker and continue on another: [NSThread
	   currentThread], thread-locals, run-loop timers (NSTimer,
	   afterDelay:) belong to whichever worker it is on -- and
	   run-loop timers in a process never fire.
	   Decided: the library reads its own per-process bookkeeping
	   in a way the compiler can't cache across a switch. The rule:
	   don't depend on which thread you're on; for timing use after
	   and sleepFor. errno is fine read right after the call that
	   set it.

	4. Exceptions. The runtime keeps per-thread state while an
	   exception is being caught.
	   Decided: a rule -- no channel operations inside @catch or
	   @finally -- and a check that stops with a clear message if
	   it's cheap to make. An uncaught exception stops the program,
	   as today and as Go's panic does.

	5. A private runtime detail -- the pool slot.
	   Decided: discovered and verified at startup, as above, with
	   the fallback.

	6. Fixed-size stacks. Decided as above: 1 MB, guard page,
	   clear overflow message; a per-process size option if deep
	   recursion ever needs it.

	7. Debugging. The debugger sees only the workers, not the
	   processes.
	   Decided:
	       deadlock detection, as Go: when every process, main
	           included, waits on a channel and no timer is
	           pending, stop with "all processes are asleep --
	           deadlock!" and what each was waiting on. Today's
	           thread version just hangs.
	       ctrl-\ prints every process, what it waits on, and
	           where it was started
	       CSP_DEBUG=threads runs every process as a real thread
	           again, so the ordinary debugger sees them all
	       ThreadSanitizer's coroutine hooks for the library's
	           own race tests

	8. No preemption. A process gives up its worker only when it
	   pauses or finishes, so a long computation keeps its core.
	   Decided: none, as before Go 1.14. The monitor asks the
	   kernel whether a busy worker is waiting or computing, and
	   adds a worker only for waiting -- 1,000 heavy computations
	   don't become 1,000 threads. When every core is computing,
	   others wait their turn and timers can fire late. yield()
	   for a long computation that wants to share.


Settings:

	CSP_MAXPROCS=n       how many cores to use (default: all).
	                     1 is a quick way to ask whether a race
	                     is involved.
	CSP_DEBUG=threads    a thread per process, the first version
	                     -- for debugging, not for running
	CSP_DEBUG=sched      adds the scheduler's counters to the
	                     deadlock report


Energy:

	What drains a battery is a program that never truly sleeps --
	waking "just to check", hundreds of times a second. The rule:
	with nothing to do, every thread sleeps in the kernel. No
	spinning, no polling.

	idle workers     wait in the kernel. A worker that just ran out
	                 of work looks again for 50 us first (Go's
	                 trick); at most half the workers do at once,
	                 and then they sleep.
	the monitor      only watches while some worker is running a
	                 process; when every process waits on a channel
	                 it sleeps too.
	timers           one kernel wait, until the earliest deadline,
	                 however many processes are sleeping. (Planned
	                 but not done: allowing macOS a little slack to
	                 coalesce nearby deadlines.)
	deadlock check   run when the last worker goes idle -- an event,
	                 not a timer.

	Measured: with 100 processes all waiting on channels, the
	program had 1 wake-up in a second (test.m). Most kernel wakeups
	-- one per message with threads -- are user-space switches now,
	and finishing sooner on all cores, then idling, is the efficient
	pattern on modern CPUs.

	Later, on Apple Silicon: workers inherit the main thread's
	quality of service, which decides fast cores or efficient
	ones. A batch job could run on the efficient cores for much
	less power -- a setting worth adding then.



Building it -- order, all done 2026-10-18:

	1. Isolate the sleep-and-wake step in today's code: no change
	   in behavior, the semaphore behind one interface.
	2. Coroutines and workers, written for all cores from the start
	   -- locks and all -- with pool swapping and slot discovery.
	   main keeps the semaphore path. Brought up first at
	   CSP_MAXPROCS=1: the same code with one worker, so the first
	   bugs (a bad switch, a lost process) repeat the same way every
	   run. The full test suite passes at 1 before going to 2, then
	   all cores; anything that breaks after is a multi-core bug by
	   elimination. Not a separate single-thread scheduler -- that
	   would be thrown away. CSP_MAXPROCS=1 stays useful after: a
	   quick way to ask whether a race is involved.
	3. Timers, sleepFor, yield.
	4. The monitor.
	5. Deadlock detection, the ctrl-\ dump, CSP_DEBUG=threads.
	6. The COOPER benchmark again, against Go; the idle-wakeups
	   test; the full test suite in both modes.

	What building it found, besides the pool pages (see above):

	the monitor's stand-in retired at once: the stuck worker still
	    counted as awake, so there seemed to be one worker too many.
	    Stuck workers are counted apart now.
	the ALT macro rewrote a variable named ALT inside the library
	    itself -- the hazard Files warns clients about.
	the deadlock detector's first catch was in its own test suite:
	    MIN(x, [c receive]) received twice, because a system header
	    defines MIN to evaluate its arguments twice. Never put a
	    channel operation inside a macro argument.

	Apple Silicon next: its own switch, slot access and stack setup
	-- a few dozen lines; everything else shared.


Memory, 2026-10-18:

	ARC cleans up everything on the normal paths. Checked with
	macOS's leaks tool: 0 leaks after the benchmark's 21,000
	processes. The test suite shows 21 small leaks, ~1 KB, all in
	tests that throw on purpose (sending nil, a Parcel opened as
	the wrong type, sending on a closed channel). That is ARC by
	design: an exception means programmer error, stop the program
	-- Go's panic -- and ARC doesn't release what it unwinds past.

	What ARC can't collect:

	a process blocked forever -- waiting on a channel nobody will
	    use again -- keeps its stack and everything it references
	    until the program exits. Go's goroutine leak;
	    a program bug, but nothing collects it.

	autoreleased objects in a long-running loop that isn't for-in
	    over a channel (a while loop, a for over an array). Those
	    are held until the process ends; wrap the body in
	    @autoreleasepool { }. for (x in c) does this for you.

	A bug found this way, and fixed: every value received, and
	every process woken, went into the receiving thread's
	autorelease pool -- ARC's default for a C function's object
	out-parameters. For a for-in worker the receive happens
	outside the loop body, out of reach of any client pool, so it
	grew ~180 bytes a message until the process ended. Measured
	over 200,000 jobs: 36 MB before the fix, flat 0.5 MB after.


Known limits:

	Deadlock detection counts main and the processes, not threads a
	program starts itself outside go(). One of those that would
	have sent to main later could see main reported as deadlocked.

	A finished process's stack is kept for reuse, never unmapped
	while the program runs (up to 65,536 of them): the first 1,024
	exactly as they are, the rest with their pages offered back to
	the kernel, as malloc does. CSP_HOT_STACKS, set when building
	the library, changes the 1,024.

	The compiler checks receive and send:, but not the value in a
	sending(c, v) case; a wrong type there is caught nowhere.

	Two anonymous structs with the same fields look like the same
	type to a Parcel. Give a struct a tag name (typedef struct
	Sample { ... } Sample) and the check can tell them apart.


Verified, 2026-10-18 (test.m, 72 checks, on the scheduler at 1 and 8
workers and with CSP_DEBUG=threads (58 apply there); clean under
ThreadSanitizer):

	unbuffered send waits for the receiver
	buffered channels: FIFO order, capacity
	close: drain, then nil; a waiting receiver gets nil; errors on
	    send-after-close, double close, and sending nil -- which
	    the compiler also warns about
	for-in as a work queue: 4 workers, 1,000 values, each once
	for-in drains a pool every pass, and break frees the last
	    value once the enclosing pool drains
	ALT: random choice among ready cases (about 50/50 over 1,000);
	    OTHERWISE only when nothing is ready; a nil channel's case
	    never fires; after's timing
	    (0.200-0.205 s for 0.2); sending; deliver-or-stop; receive
	    on a closed channel fires with nil; return from a case
	receive(x, c) types x from Chan<T> -- checked at compile time
	a case that never fires leaves nothing queued, over 5,000 alts
	Parcel: round trip, the copy, wrong-type and closed-channel
	    errors; anonymous structs alike, tagged ones told apart
	pools spanning pages, opened and closed on different workers
	1,900 processes live at once; 20,000 on the scheduler
	stress: 6 senders, 5 receivers, 3 unbuffered channels, all
	    through ALT -- 18,000 values, each received exactly once;
	    6 processes offering both sending and receive on one
	    channel -- sends and receives balance
	sleepFor: 200 processes sleeping 0.2 s each take 0.2 s in all
	yield: with one worker, a computing process lets another run
	the monitor: with one worker, a process blocked in read() on a
	    pipe doesn't stop the process that writes to it
	after inside processes: 100 timeouts at once
	idle: 100 processes all waiting -- 1 wake-up in a second
	ending the program, each in a copy of csptest: the deadlock
	    report (exit 2, with what main and each process waits on
	    and where it started); the stack overflow message; a
	    channel operation inside @catch stopped; ctrl-\ dumps every
	    process (exit 2)

	The first stress runs failed about one in three: each process
	reported two numbers as two sends on a shared channel, and
	reports from different processes interleaved. A test bug, not
	a library one -- the fix was one message per report. Worth
	remembering as a pattern: a reply that must stay together goes
	in one message.
